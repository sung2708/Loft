# Authentication, Identity & Permissions Architecture — Loft

## 1. Identity Separation: Authenticated Users vs. Guests

Loft supports frictionless social hangouts. Users can join instantly as guests without friction or sign in with permanent credentials to maintain persistent identity.

```
                  ┌──────────────────────────────────────────────┐
                  │             Incoming Connection              │
                  └──────────────────────┬───────────────────────┘
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 │                                               │
                 ▼ (Has Supabase JWT)                            ▼ (No Account / Guest)
   ┌───────────────────────────┐                   ┌───────────────────────────┐
   │     AUTHENTICATED USER    │                   │       GUEST IDENTITY      │
   ├───────────────────────────┤                   ├───────────────────────────┤
   │ - Issued by Supabase Auth │                   │ - Ephemeral Room-Scoped   │
   │ - Backed by `users` table │                   │ - HMAC-SHA256 signed by Go│
   │ - Persistent profile & ID │                   │ - Expire in 24 hours      │
   │ - Can own permanent rooms │                   │ - Cannot own rooms        │
   └───────────────────────────┘                   └───────────────────────────┘
```

## 2. Token Verification in Go

The Go backend **never** trusts client-declared identities, roles, or permissions. All tokens are cryptographically verified:

1. **Supabase JWTs:**
   - Go fetches and caches the Supabase project JWKS (JSON Web Key Set).
   - Validates signature (`RS256` or `HS256`), issuer (`iss`), audience (`aud`), and expiration (`exp`).
   - Extracts `sub` (durable `user_id`).

2. **Guest Identity Tokens:**
   - Generated by Go upon joining via invite link:
     $$\text{Token} = \text{Base64Url}(\text{Payload}) + "." + \text{HMAC-SHA256}(\text{Secret}, \text{Payload})$$
   - Payload contains: `{ "guest_id": "uuid", "room_id": "uuid", "display_name": "Guest Otter", "exp": 1789389200 }`.
   - **Room-Scoped Constraint:** A guest token issued for Room A cannot be used to authenticate into Room B.

## 3. Role Hierarchy & Explicit Permissions

Roles provide sensible defaults, but authorization decisions are evaluated against **explicit capabilities**:

| Capability | Host | Moderator | Member | Guest |
| :--- | :---: | :---: | :---: | :---: |
| `can_change_room_settings` | Yes | No | No | No |
| `can_transfer_host` | Yes | No | No | No |
| `can_assign_moderator` | Yes | No | No | No |
| `can_ban` | Yes | Yes (Non-mods) | No | No |
| `can_kick` | Yes | Yes (Non-mods) | No | No |
| `can_share_screen` | Yes | Yes | Yes (Default) | Optional |
| `can_control_media` | Yes | Yes | Yes (Default) | Optional |
| `can_manage_queue` | Yes | Yes | Yes (Default) | Yes |
| `can_send_chat` | Yes | Yes | Yes | Yes |

## 4. Centralized Authorization Domain Engine

Authorization logic is centralized in `internal/permissions/evaluator.go`. Transport handlers (HTTP/WS) must **never** inspect roles directly with raw strings like `if role == "host"`.

### Go Evaluator API Contract

```go
package permissions

type Evaluator interface {
    CanChangeSettings(actor *Subject, room *RoomState) bool
    CanTransferHost(actor *Subject, room *RoomState) bool
    CanAssignModerator(actor *Subject, room *RoomState) bool
    CanKick(actor *Subject, target *Subject, room *RoomState) bool
    CanBan(actor *Subject, target *Subject, room *RoomState) bool
    CanShareScreen(actor *Subject, room *RoomState) bool
    CanControlMedia(actor *Subject, room *RoomState) bool
    CanManageQueue(actor *Subject, room *RoomState) bool
}
```

### Hierarchy Enforcement Example: `CanKick`
A moderator cannot kick the room host or another moderator:

```go
func (e *evaluator) CanKick(actor, target *Subject, room *RoomState) bool {
    if actor.ID == target.ID {
        return false // Cannot kick self via moderation API
    }
    if actor.ID == room.HostID {
        return true // Host can kick anyone
    }
    if actor.Role == RoleModerator {
        // Moderator can only kick regular members and guests
        return target.Role == RoleMember || target.Role == RoleGuest
    }
    return false
}
```

## 5. Row-Level Security (RLS) & Direct Database Guardrails

If Supabase direct client access is enabled for any read tables, strict RLS policies must prevent unauthorized data exposure:

1. **`rooms`:** Public rooms readable by all; private rooms readable only by active members.
2. **`messages`:** Readable only by users with an active membership record in that room.
3. **Mutations Blocked:** All state-mutating operations (`host_id`, `role`, `bans`, `permissions`) are **blocked** in RLS from direct client updates (`FOR UPDATE TO authenticated USING (false)`). Mutations must route exclusively through the Go backend API.
